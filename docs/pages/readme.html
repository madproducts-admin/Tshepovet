TshepoVet README

TshepoVet is a low-cost B2B vendor onboarding, KYB and continuous-compliance platform for South Africa. A company legitimacy check (CIPC registration, active directors, VAT, SARS tax compliance) costs R3.00 and a driving licence or PrDP check costs R2.50. Every verified supplier gets a free, shareable Verified Vendor Passport.

3Quick start

Requirements: Node 20+, PostgreSQL 16 and Redis 7. The app must connect as a role without superuser or BYPASSRLS; otherwise row-level security is silently skipped.

Shell
npm install

# 1. Database roles: an owner that runs migrations, and an app login role WITHOUT
#    superuser/BYPASSRLS so row-level security is actually enforced.
psql -c "CREATE ROLE tshepovet_owner LOGIN SUPERUSER PASSWORD 'devpass';"
psql -c "CREATE DATABASE tshepovet_dev OWNER tshepovet_owner;"
export MIGRATION_DATABASE_URL=postgres://tshepovet_owner:devpass@localhost:5432/tshepovet_dev
npx tsx scripts/migrate.ts
psql "$MIGRATION_DATABASE_URL" -c "CREATE ROLE tshepovet_api LOGIN PASSWORD 'apipass' IN ROLE tshepovet_app;"

# 2. Secrets (dev only) and a demo tenant with R1,000 credit + live/test API keys
cp .env.example .env   # then fill the three 32-byte base64 keys:
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
set -a; source .env; set +a
npx tsx scripts/seed-dev.ts      # prints tenant id and API keys

# 3. Run
npm run dev
curl -s localhost:8080/v1/verify/company \
  -H "Authorization: Bearer <tv_live_ key from seed>" -H 'Content-Type: application/json' \
  -d '{"registration_number":"CK2001/012345/23","vat_number":"4123456789","checks":["registration","directors","vat"]}'

With ENABLED_PROVIDERS=mock (the default outside production), live keys hit the deterministic mock bureau. Sandbox tv_test_ keys always do, and are free. The test values that trigger each scenario are listed on the Verification API page.

4Tests

Shell
npm test            # 82 tests: unit + integration
npm run typecheck

The integration suite rebuilds a real PostgreSQL database from db/migrations/ and connects as the non-superuser app role, so every test runs under row-level security. It exercises the HTTP API end to end:

  • R3.00 wallet capture and ledger balance
  • Shared cache for public data, tenant-only TCS results
  • Idempotent replay
  • 402 with nothing created
  • Bureau failover
  • No charge when all bureaus are down
  • Consent enforcement
  • Tenant isolation
  • Signed webhook delivery
  • Audit-chain integrity
  • Crypto-shredding by the retention purge

6Known gaps before production

  • IntegrationBureau adapters (httpBureau.ts) use placeholder endpoints and field mappings. Map them from each bureau's signed integration guide, and confirm which bureaus actually offer TCS and eNaTIS products.
  • IntegrationThere is no public SARS TCS API. Choose a lawful fulfilment channel (Architecture & Compliance §2.8).
  • BuildAsync verifications run in-process. Move them to a durable queue such as SQS or BullMQ (§1.9).
  • BuildLocalKeyProvider needs replacing with AWS KMS in af-south-1.
  • BuildNot yet built: the secure TCS link and WhatsApp Flow endpoint, the ClamAV scan, EXIF stripping and pHash (WhatsApp Onboarding §6), the ERP connectors, and the B-BBEE scorecard and conflict-of-interest workers. The schema supports all of them.
  • LegalLegal review is required for the privacy notice wording, the roles matrix and the POPIA s57 assessment of the conflict-of-interest radar (§2.6).
