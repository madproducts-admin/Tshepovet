TshepoVet Verification API

Verify a South African company (CIPC registration, directors, VAT, SARS tax compliance) or a driver's licence and PrDP with one request. Funds are reserved from your prepaid wallet before any bureau is called and charged only when a definitive answer comes back.

R3.00company check, VAT-exclusive
R2.50driving licence and PrDP check
~8 ssync wait; longer checks return 202 and a webhook
24 hIdempotency-Key replay window
50 / sdefault rate limit per key on verify endpoints

  • Authentication: Authorization: Bearer tv_live_xxxxxxxx.<secret>. Sandbox keys start with tv_test_, are free, and only ever reach the deterministic mock bureau.
  • Idempotency: send Idempotency-Key on every POST. Retrying with the same key and body returns the original response with Idempotent-Replayed: true and never charges twice.
  • Sync or async: mode: sync (the default) waits up to about 8 seconds. If checks are still running you get 202 with status: processing; the result arrives by webhook and at GET /v1/verifications/{id}.
  • Contract: openapi/openapi.yaml. A contract test keeps it in sync with the route validators: request fields must match the schemas, every reference must resolve, and the examples must validate.

2POST/v1/verify/company

Checks the CIPC registration and status, active directors, VAT registration and, with the vendor's PIN, the SARS tax compliance status. A TCS check needs consent covering tax_compliance_verification; monitor: true also needs continuous_monitoring and enrols the vendor in expiry monitoring at R15 per vendor per month.

Request · curl
curl -s https://api.tshepovet.co.za/v1/verify/company \
  -H "Authorization: Bearer $TSHEPOVET_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: onboard-SUP-0001-v1" \
  -d '{
    "registration_number": "2019/123456/07",
    "vat_number": "4123456789",
    "tax_reference_number": "9123456789",
    "tcs_pin": "AB12CD34EF",
    "checks": ["registration", "directors", "vat", "tcs"],
    "external_ref": "SUP-0001",
    "monitor": true,
    "consent": {
      "notice_code": "company_verification",
      "subject_display": "ACME TRADING (PTY) LTD",
      "subject_role": "authorised_representative",
      "purposes": ["tax_compliance_verification", "continuous_monitoring"],
      "captured_at": "2026-11-14T08:00:00+02:00",
      "evidence_reference": "onboarding-form-8812",
      "attested_by": "procurement@buyer.example"
    }
  }'

registration_number accepts 2019/123456/07, 2019-123456-07, 201912345607, and the CK and K prefixes. Without vat or tcs in checks, no consent is needed.

Reading the response

verifiedverified_with_warningsfailed_checksnot_foundunable_to_verify
  • outcome is decision support (POPIA s71). Your team makes the onboarding decision.
  • checks.<name>.source and data_as_of show whether data came from cache, a bureau, or stale cache served during an outage (stale: true).
  • risk_flags are stable codes to branch on, for example cipc_status_deregistration_process, vat_number_registered_to_different_name, sars_non_compliant, tcs_pin_expired and director_appointed_within_30_days.
  • Director ID numbers come back as the last four digits only. The TCS PIN is never echoed, logged or sent in webhooks.
  • billing.charged and billing.wallet_balance_cents report the charge. If every provider fails you get unable_to_verify and charged: false.

3POST/v1/verify/driver-license

The driver is a natural person who is not party to your contract, so consent is always required: either a consent_id captured by TshepoVet, or an attestation by the employer (on_behalf_of_subject: true) with an evidence reference you can produce on request.

Request · curl
curl -s https://api.tshepovet.co.za/v1/verify/driver-license \
  -H "Authorization: Bearer $TSHEPOVET_KEY" -H "Content-Type: application/json" \
  -H "Idempotency-Key: driver-8001015009087-2026-11" \
  -d '{
    "id_number": "8001015009087",
    "licence_number": "400100001234",
    "surname": "Mokoena",
    "required_codes": ["C1"],
    "required_prdp": ["G"],
    "vendor_id": "01a1dc4f-3f43-7a5d-8b21-0fd5fadd8d77",
    "consent": {
      "notice_code": "driver_verification",
      "subject_display": "T. Mokoena",
      "subject_role": "driver",
      "on_behalf_of_subject": true,
      "purposes": ["driver_licence_verification"],
      "captured_at": "2026-11-14T08:00:00+02:00",
      "evidence_reference": "driver-consent-form-77",
      "attested_by": "fleet@logistics.example"
    }
  }'
  • required_codes follows the licence code hierarchy: EC1 satisfies a C1 requirement, but EC1 does not satisfy C.
  • PrDP categories (G, P, D) must match exactly by default. A category D holder under 25 is flagged.
  • Gazetted grace periods for licence-card backlogs come back as licence_in_gazetted_grace_period, a warning rather than a failure.
  • The id_number is checked locally (13 digits, Luhn check digit, plausible date of birth) before anything is charged.

5Handler anatomy

What POST /v1/verify/company does, in order:

Request pipeline
requestContext      -> X-Request-Id
apiKeyAuth          -> authenticate_api_key(prefix) + constant-time HMAC compare + scope
rateLimit           -> Redis fixed window per key (50 rps)
idempotency         -> claim / replay / 409 / 422
zod parse           -> CompanyRequestSchema (.strict(): unknown fields rejected)
SA normalisation    -> VAT (4xxxxxxxxx), tax ref, TCS PIN
CompanyVerificationService.start()
  TX1: resolve vendor (definer fn) -> link -> consent -> insert verification -> RESERVE hold
  process(): parallel resolve(registration | vat | tcs) via cache -> waterfall
  TX2: persist vendor/directors/PIN -> checks -> provider_calls -> CAPTURE|RELEASE -> outbox -> audit
respond()           -> 200 (done) | 202 (still processing) + Location
errorHandler        -> RFC 9457 problem+json with a stable code

The wallet deduction (src/billing/wallet.ts) is one atomic statement, with a database constraint behind it:

Reserve · SQL
UPDATE wallets SET held_cents = held_cents + $2
 WHERE tenant_id = $1 AND status = 'active'
   AND balance_cents - held_cents + credit_limit_cents >= $2
RETURNING id;            -- no row => 402 insufficient_funds

The capture moves the hold into the balance and posts two ledger entries (debit the customer wallet, credit usage revenue) under the idempotency key capture:<hold_id>. The Database Schema page lists every billing invariant the database enforces.

6Receiving webhooks

Events are thin: ids, statuses and flags only. Fetch details with GET /v1/verifications/{id}. Delivery is at least once, so deduplicate on the event id. Failed deliveries are retried with exponential backoff for about 36 hours.

HeaderValue
TshepoVet-Signaturet=<unix time>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>; several v1 values during secret rotation
TshepoVet-Event-IdEvent id; use it to deduplicate
TshepoVet-Event-Typeverification.completed, verification.failed, wallet.low_balance, vendor.payment_locked, …
TshepoVet-Delivery-Attempt1 for the first attempt
Receiver · TypeScript / Express
import crypto from 'node:crypto';
import express from 'express';

const app = express();
app.post('/tshepovet/webhooks', express.raw({ type: 'application/json' }), (req, res) => {
  const header = req.header('tshepovet-signature') ?? '';
  const parts = Object.fromEntries(header.split(',').map((p) => p.split('=') as [string, string]));
  const t = Number(parts.t);
  if (!t || Math.abs(Date.now() / 1000 - t) > 300) return res.sendStatus(400); // replay window
  const expected = Buffer.from(crypto.createHmac('sha256', process.env.TSHEPOVET_WEBHOOK_SECRET!).update(`${t}.${req.body}`).digest('hex'));
  const ok = header.split(',').some((p) => {
    const sig = Buffer.from(p.startsWith('v1=') ? p.slice(3) : '');
    return sig.length === expected.length && crypto.timingSafeEqual(sig, expected);
  });
  if (!ok) return res.sendStatus(401);
  const event = JSON.parse(req.body.toString('utf8'));
  // enqueue(event): respond fast, process asynchronously and idempotently on event.id
  res.sendStatus(204);
});

Verify against the raw body, not re-serialised JSON. src/webhooks/signing.ts holds the reference implementation.

7Errors

Errors are RFC 9457 application/problem+json with a stable code to switch on and a request_id to quote to support. Nothing is created or charged on any 4xx.

8Running locally

Requires Node 20+, PostgreSQL 16 and Redis 7. The app must connect as a role without superuser or BYPASSRLS, otherwise row-level security is silently skipped.

Quick start · shell
npm install
# owner role runs migrations; the app role has no superuser/BYPASSRLS
psql -c "CREATE ROLE tshepovet_owner LOGIN SUPERUSER PASSWORD 'devpass';"
psql -c "CREATE DATABASE tshepovet_dev OWNER tshepovet_owner;"
export MIGRATION_DATABASE_URL=postgres://tshepovet_owner:devpass@localhost:5432/tshepovet_dev
npx tsx scripts/migrate.ts
psql "$MIGRATION_DATABASE_URL" -c "CREATE ROLE tshepovet_api LOGIN PASSWORD 'apipass' IN ROLE tshepovet_app;"

# secrets: fill the three 32-byte base64 keys in .env
cp .env.example .env
set -a; source .env; set +a
npx tsx scripts/seed-dev.ts    # demo tenant, R1,000 credit, live + test keys

npm run dev
npm test                       # 81 unit + integration tests
