TshepoVet Database Schema

The data model behind vendor passports, consent, billing and audit. Tenant isolation, overspend protection, ledger balance and audit integrity are enforced by PostgreSQL itself, so an application bug cannot break them. The test suite rebuilds the database from these exact migrations on every run, connected as a non-superuser, so row-level security is exercised for real.

The DDL is in db/migrations/0001_init.sql and the reference data in 0002_seed_reference_data.sql. Vendors are global: one row per legal entity across all buyers. Everything a buyer owns hangs off tenants.

3Billing invariants enforced by the database

InvariantMechanism
A buyer can never spend credit they don't have, even under an application bugCONSTRAINT wallet_no_overspend CHECK (balance_cents - held_cents + credit_limit_cents >= 0)
Every ledger transaction balancesA DEFERRABLE INITIALLY DEFERRED constraint trigger, assert_ledger_balanced(): the entries must sum to zero at commit
The ledger is immutableforbid_mutation() triggers plus REVOKE UPDATE, DELETE
A hold is captured at most onceThe hold moves from active to captured in a single UPDATE … WHERE status = 'active', and the ledger's idempotency_key = 'capture:<hold_id>' is UNIQUE
Top-up VAT arithmeticCHECK (gross_cents = credit_cents + vat_cents). Credits are VAT-exclusive, with 15% VAT invoiced on top-up. Confirm the time-of-supply treatment of prepaid credits with your tax adviser.
One hold per verificationUNIQUE (reference_type, reference_id)
A vendor's monitoring is never billed twice for the same periodEXCLUDE USING gist (tenant_vendor_id WITH =, period WITH &&)

The sign convention is debit positive, credit negative. The customer wallet is a liability (TshepoVet owes the buyer checks), so a top-up credits it and a usage capture debits it, with the opposite leg on revenue_usage. wallets.balance_cents is a projection of that account, and the integration test asserts that the projection equals the ledger.

One R3.00 check, as ledger entries

-- reserve: no ledger entry, only wallets.held_cents += 300
-- capture, transaction kind 'usage_capture', idempotency_key 'capture:<hold_id>'
Dr  customer_wallet   +300   -- liability falls: the buyer has used a check
Cr  revenue_usage     -300
-- release (provider outage): held_cents -= 300, no ledger entry

4Audit hash chain

Each tenant has its own chain. Every row's hash covers the previous row's hash, so editing or deleting any row breaks every hash after it.

audit_log_hash()

SELECT sha256(p_prev || convert_to(concat_ws('|', p_seq, p_key, r.actor_type, r.actor_id, r.action,
              r.entity_type, r.entity_id, r.request_id, r.details::text,
              to_char(r.occurred_at AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US')), 'UTF8'));
  • audit_log_chain() is a SECURITY DEFINER BEFORE INSERT trigger. It locks the tenant's audit_chain_heads row, assigns chain_seq = last_seq + 1, and links the row to the previous hash. Because the sequence number is assigned under the lock, chain order equals chain_seq order even when transactions interleave.
  • The app role has no access to audit_chain_heads and no UPDATE or DELETE on audit_log.
  • verify_audit_chain(tenant) returns the first broken chain_seq, which catches both edits and deletions (gaps). The smoke tests confirm it catches a superuser rewrite. For external anchoring, publish each tenant's daily head hash somewhere TshepoVet can't rewrite, such as the tenant's own webhook or an append-only bucket.
  • Monthly partitions older than seven years are dropped, per the audit_log retention policy.

tenant_can_see_vendor()

SELECT EXISTS (SELECT 1 FROM tenant_vendors tv
                WHERE tv.vendor_id = p_vendor AND tv.tenant_id = current_tenant_id())
    OR EXISTS (SELECT 1 FROM vendor_passport_shares s
                WHERE s.vendor_id = p_vendor AND s.tenant_id = current_tenant_id()
                  AND s.revoked_at IS NULL AND (s.expires_at IS NULL OR s.expires_at > now()));

There is deliberately no INSERT policy on vendors. Tenants create passports only through resolve_vendor_by_cipc() and resolve_vendor_sole_proprietor(), which deduplicate on the natural key and return only an id, so a tenant can't probe which companies other buyers work with. API-key authentication goes through authenticate_api_key(), because RLS hides api_keys until the tenant is known.

Operational requirement

The schema-owner role must have BYPASSRLS (or be the RDS master user), because FORCE ROW LEVEL SECURITY also applies to table owners and the definer functions rely on that bypass. The API connects as a separate login role that is a member of tshepovet_app and has no BYPASSRLS. Workers that legitimately span tenants (webhook dispatch, purge, monitoring, WhatsApp routing) use tshepovet_worker.

6Retention (POPIA s14) in the schema

Every table holding personal information has a purge-date column, filled at write time from ref_retention_policies. run_retention_purge(batch), which only the worker role can execute, then does the following:

DataAction
TCS PINs past expiry, revoked or invalidpin_enc := NULL (crypto-shred), status := 'purged'; status history kept
Raw bureau payloads (30 days)response_enc := NULL
Document imagesThe worker deletes the S3 object (all versions), then sets storage_key := NULL
Document records past retentionextracted_fields_enc := NULL, document_number_bidx := NULL
Cache rows past stale_untilDELETE
Verification results past retentionresult := NULL, subject_display := '[purged]'; the billing record is kept for tax purposes
Director ID numbers past retentionid_number_enc := NULL
HR imports (30 days after last activity)DELETE
WhatsApp message metadata (30 days), idempotency keys (24 hours)DELETE

Each run writes a purge_runs row and a retention.purged audit event with counts, which is the evidence for the Information Regulator. Backups can't be rewritten, so deletion there relies on crypto-shredding: a purged row has no ciphertext left in live data, and backup ciphertexts become unrecoverable when the key version that wrapped them is retired at the end of the backup retention window.

7Running migrations

MIGRATION_DATABASE_URL=postgres://owner:***@host:5432/tshepovet npx tsx scripts/migrate.ts

The migrator is forward-only and records applied files in schema_migrations. Each file runs as a single transaction.
